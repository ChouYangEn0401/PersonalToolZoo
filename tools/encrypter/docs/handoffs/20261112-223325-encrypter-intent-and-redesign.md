  還沒合併回 master、還沒打包、畫面還沒有人看過；合併後把這一行改成「已修」並寫上 merge commit）
- 建立：2026-11-12 ｜ 範圍：`tools/encrypter/`
- 開發線：`dev/encrypter`，開工前 `git merge master`
- **寫給接手的 agent**：先讀這張，再讀 `../legacy-modes.md`（舊功能在哪、怎麼救回）與 `../ui-spec.md`（新介面規格與驗收清單）。
  新程式在 `crypto_tool/sealed/`（格式、金鑰、檔案操作、命令列）與 `crypto_tool/gui/app.py`／`logic.py`／`texts.py`。
  舊程式（`core/`、`gui/tab_*.py`）**不要改、不要刪**。

## 問題一句話

這個工具把「加密一個檔案」做成了要先懂十一種演算法、迭代次數與兩種 Mixture 模式才能用的介面；
而最花力氣、一直改不對的 Layered／Nested 兩種 Mixture 模式，在加密上其實是同一件事，也不會更安全——
問題出在需求本身，不是出在實作細節，所以怎麼改都改不「對」。同時它沒有命令列，別的程式沒辦法呼叫。

## 脈絡

### 這個工具原本想做什麼

- 一個自己用的桌面加密工具：選檔案、輸入密碼、得到一個只有自己打得開的檔。
- 一路加上去的想法：自己的檔案格式（`.isd`）、很多種演算法可以選、拿圖片或影片當鑰匙、加密一段文字、
  多位收件人（PGP 系列）、第三方保管鑰匙（Escrow）、大檔分段，以及「多階段混合」（Mixture）。
- 從文件看得出來的動機是「**疊得越多、越特別，就越安全**」以及「**只有我這個程式解得開**」。
  這兩個直覺在加密上都不成立（見下面），是後面所有困難的來源。

### Mixture 兩種模式想達成的目標

| | 想要的效果 | 適合的情境（文件自己寫的） | 名字的演變 |
|---|---|---|---|
| 模式 A「全部融合」 | 同一份資料用好幾把鑰匙連續加密，最後只有**一個**檔；鑰匙**缺一把就完全解不開**，中途解一次只會看到亂碼 | 必須一口氣完整解開 | Simple → Layered → **All-In-One**（現在程式裡的名字） |
| 模式 B「一層一層」 | 每加密一次就包成一個完整的檔，像俄羅斯娃娃；解一次得到**下一層完整的檔**，可以交給下一個人繼續解 | 逐步解鎖、分段授權（不同的人各解一層） | Node → Nested → **Layered**（現在程式裡的名字） |

換成白話，背後其實是兩個合理的需求：**A＝「要好幾把鑰匙都到齊才能開」**、**B＝「要照順序、一關一關由不同的人開」**。

### 為什麼做不好

**設計上（根本原因）**

1. **A 和 B 在加密上是同一件事。** 兩者都是「加密之後再加密」。差別只有 B 在每一層中間多包了一次 base64 與一段 JSON。
   所以「解一次會看到亂碼還是看到下一層的檔」是**包裝**的差別，不是安全性的差別。開發紀錄裡反覆在調的正是這個包裝行為。
2. **疊加不會更安全。** AES-256 加密一次，已經遠超過任何人能硬解的程度；實際的弱點永遠是「密碼好不好猜」與「鑰匙有沒有保管好」。
   多疊幾層補不了好猜的密碼。同一個密碼加密 N 次（File 分頁的 Iterations）強度完全沒有增加，只是變慢。
3. **名字換了三輪而且互相撞名。** 「Layered」在較早的版本指 A，在現在的版本指 B。
   結果：外層 README 與 `del_dev_plan.md` 用舊的意思，`crypto_tool/dev_plan.md` 與程式用新的意思，
   `crypto_tool/README.md` 開頭用新的、後半段「兩種加密模式」又用舊的。連文件都講不清楚，使用者與接手的人更不可能弄對。
4. **「只有本程式解得開」「把演算法藏起來」沒有加密上的意義。** 格式就是 base64 加一段明文 JSON，誰都讀得懂；
   安全性只能來自鑰匙，不能來自「別人不知道我怎麼做的」。

**技術上（實際的缺陷，都在 `crypto_tool/core/` 與 `gui/tab_file.py`）**

| # | 缺陷 | 白話的後果 | 位置 |
|---|---|---|---|
| 1 | 預設的 AES-256-CBC 沒有完整性驗證 | 加密檔被人改過，解密不一定會發現；可能解出被動過手腳的內容 | `core/engine.py` `AES_CBC` |
| 2 | 「密碼打錯」是靠解出來的結尾格式不對才知道 | 大約每 256 次有一次會把錯的密碼當成對的，吐出亂碼；多階段時錯誤訊息變成看不懂的 padding 錯誤 | 同上；紀錄裡的「wrong padding 問題」就是這個 |
| 3 | `NOTE`（檔案說明）是明文、而且沒有受保護 | 檔名、大小、作者、密碼提示、用了哪些演算法，拿到檔案的人都看得到，也都能改（例如把密碼提示換掉） | `core/bytefile.py` |
| 4 | **XOR-FOLD 只改到前 32 個 bytes** | 用這個「演算法」加密的檔案，從第 33 個 byte 開始全部是原文 | `core/engine.py` `XORFoldCipher`（迴圈只跑金鑰的長度） |
| 5 | XOR 是 32 bytes 的金鑰重複使用；Base64 不是加密；3DES、Blowfish 已經過時 | 這些跟 AES 排在同一排讓人選，選到就等於沒有保護或保護很弱 | `core/engine.py`、`gui/widgets.py` `AlgoBar` |
| 6 | 舊檔的 `mode` 可能被讀反 | 更早版本存的 `"layered"` 意思是 A，現在的程式把它當成 B 來解 | `core/bytefile.py` 的 `mode`（只轉換了 simple／node／nested，沒處理撞名的 layered）；`default_note` 的預設值也還是舊的意思 |
| 7 | PGP-Escrow 的「有第三方能解」只記在沒受保護的 `NOTE` 裡 | 那個標記可以被拿掉，收件人不會知道還有第三把鑰匙解得開。Escrow 與 Multi 在加密上完全相同 | `core/pgp.py`、`gui/tab_file.py` |
| 8 | 名字叫 PGP 但不是 OpenPGP | 跟 gpg 或任何 PGP 軟體都不相容；是自己排的 RSA＋AES-GCM 信封（用的元件本身是標準的） | `core/pgp.py` |
| 9 | 密碼轉金鑰用 PBKDF2 十萬次 | 低於現在的建議值；每一層、每一次迭代都重算一次，所以又慢又沒比較安全 | `core/engine.py` |
| 10 | 整個檔案讀進記憶體，每層再膨脹三分之一 | 大檔、多層時很吃記憶體，B 模式三層就接近原檔的 2.4 倍 | `core/pipeline.py`、`core/bytefile.py` |
| 11 | Large File 是另外寫的一套，`manifest.json` 沒有保護 | 塊被調換或抽掉不會發現；介面上自己標著 UNTESTED | `gui/tab_largefile.py` |
| 12 | 加密邏輯散在介面程式裡，跟 `pipeline.py` 重複 | 計畫書寫「介面不含加密邏輯」，實際上 File 分頁自己又做了一套分層與 PGP；改一邊另一邊就不一致 | `gui/tab_file.py` `_encrypt_worker`／`_decrypt_worker` |
| 13 | 測試只有 7 個，都是「正常會成功」的情況 | 其中一個測試不管結果如何都會過；沒有任何竄改、截斷、錯誤格式的測試 | `tests/test_mixture_modes.py` |
| 14 | 錯誤直接把程式的英文例外丟給使用者 | 看到的是 `Padding is incorrect.` 這類訊息，不知道是密碼錯還是檔案壞 | 各 `gui/tab_*.py` |

（第 4、6 項是讀程式確認的；這台電腦沒有 pycryptodome，沒有實際執行舊程式。）

### 已經做的（這一輪）

- **新格式 ISD2 與命令列**（`crypto_tool/sealed/`，`5061fb8`）：AES-256-GCM／ChaCha20-Poly1305、密語走 scrypt、
  分塊加密、檔頭與每一塊都驗證；改動、對調、截斷、結尾加料、鑰匙不對都會明確失敗，而且不留下半個輸出檔。
  `python -m crypto_tool encrypt|decrypt|info|keygen`，有 `--json` 與固定的退出碼。
- **新介面**（`27e5d43`）：加密／解密／金鑰／關於；簡單模式是預設；主視窗沒有 Mixture。
- **舊功能保留**：程式沒刪，收進「關於 → 開啟舊版工具」，標成實驗性。細節與救回方法在 `../legacy-modes.md`。

### 哪些保留、重做、封存

| 東西 | 處置 | 原因 |
|---|---|---|
| 「選檔案、給鑰匙、得到加密檔」這個核心用途 | **重做（已做）** → ISD2 | 用標準做法，一種就夠 |
| 資料夾、大檔 | **重做（已做）** → ISD2 內建（邊打包邊加密、分塊） | 取代 Large File 分頁 |
| 命令列 | **新增（已做）** | 讓別的程式呼叫 |
| 拖放、密碼提示強度、進度、人話訊息 | **保留想法，重寫（已做）** | 舊介面裡好用的部分 |
| `.isd` 格式、十一種演算法、兩種 Mixture、PGP 系列、Large File、Text 分頁 | **封存**（留在舊版工具，只建議用來解舊檔） | 見上表；不再加功能、不再修 |
| 「好幾把鑰匙都到齊才能開」（A 的真正需求） | **之後若需要再做**，做法見選項 B | 現在沒有人在用 |
| 「多人各自能開」「一關一關開」（PGP／B 的真正需求） | **之後若需要再做**，做法見選項 C | 同上 |
| XOR、XOR-FOLD、Base64 當成「加密」 | **不再提供** | 沒有保護力 |

## 選項表

之後這個工具要往哪裡走。**預設做 A（已經照 A 做了）**；B、C 要等擁有者說真的需要。

| 選項 | 內容 | 建議 |
|---|---|---|
| A | 主線只留 ISD2（一種標準做法）；舊功能留在舊版工具，只用來解舊檔 | **建議（預設，已實作）** |
| B | 加「多把鑰匙都到齊才能開」：把幾個鑰匙來源（例如密語＋金鑰檔＋隨身碟上的鑰匙）用 HKDF 合成一把，仍然只加密一次。不是疊加密 | 有實際需要再做；工作量小（`sealed/keys.py` 加一個合成函式＋檔頭記來源數量） |
| C | 加「多人各自能開」：每位收件人用自己的公鑰包同一把檔案金鑰（X25519，做法同 age）；要「一關一關」就讓每一關的人各包一層，這時巢狀才有意義 | 有實際需要再做；工作量中等，要先決定公鑰怎麼交換與保管 |
| D | 把舊的 Mixture 修到「對」 | **不做**：需求本身沒有加密上的意義，修不出比 A 更安全的東西 |
| E | 把舊功能整個刪掉 | **不做**：舊檔會打不開，也違反「過去的東西不刪」 |

另外幾件要擁有者決定的小事（都有預設，不回答就照預設）：

| 題目 | 選項 | 建議 |
|---|---|---|
| 手上還有重要的舊 `.isd` 檔嗎 | 有 → 用舊版工具解開、用新格式重加密一次／沒有 → 不用管 | 有的話趁舊版工具還在先轉掉 |
| 別的程式要讀加密的設定檔時，解密結果要不要能直接從標準輸出拿（不落地成檔案） | 不提供（現在）／加 `decrypt --stdout` | 先不提供；要做時再加，並限定只在非終端機時允許 |
| 新格式的副檔名 | `.isd2`（現在）／其他 | 維持 `.isd2`：看得出是同一個工具的第二代，又不會跟舊檔混在一起 |
| 隨身碟鑰匙（另一個專案）要不要接進來 | 先不接：由呼叫端把鑰匙放進環境變數，再用 `--key-env`（現在就能用）／直接整合 | 先不接；工具之間互不依賴 |

## 不要做的事

- 不要刪或改 `core/`、`gui/tab_*.py`、`gui/widgets.py`；舊檔要靠它們解。
- 不要把 Mixture、迭代次數、XOR、Base64 這些選項放回主視窗。
- 不要自己發明加密步驟或「混合」方式。要新功能就用選項 B、C 寫的標準做法。
- 不要讓密語可以從命令列引數傳入；不要在任何輸出、紀錄、錯誤訊息裡放金鑰、密語、明文。
- 不要改 ISD2 第 1 版的檔頭排法（已經有檔案用它加密了）；要改就升格式版本，舊版本照樣要解得開。
- 不要把真的金鑰、`.env`、個人資料寫進 repo；測試用的金鑰在測試執行時產生。
- 不要自己 push、打 tag、發版；版本號用 `scripts/bump-version.ps1` 或 `release.ps1` 改，不要手打。
