## 需求（改寫，非原話）

- 要一個可以放心拿來保護備份與祕密的加密核心，取代現有的多演算法混合做法。
- 同一個核心要能被這個 repo 的介面使用，也要能被擁有者另一個專案（自架的 AI 助理核心）以「指令＋機器可讀輸出」的方式呼叫。
- 密語與金鑰不得出現在命令列歷史、日誌或 AI 對話裡。

## 問題一句話

用標準且經過公開審查的演算法與函式庫，做一個**只有一種安全做法**的加解密核心：有版本的格式、分塊串流、任何竄改與截斷都會被發現、舊 `.isd` 只讀不寫。

## 設計原則

1. **不自創密碼學**：只組合標準原語（認證加密、密語衍生、金鑰衍生），而且組合方式也照既有、被分析過的做法。
2. **只有一條路**：使用者不選演算法、不選模式、不疊層。能調的只有「誰可以解開」（金鑰槽／收件者）。
3. **驗證通過才交出明文**：解密失敗時不留下半成品。
4. **格式自己描述自己**：魔術字、版本、參數都在檔頭，而且檔頭受驗證保護；讀到不認識的版本要明確拒絕。
5. **祕密走專用管道**：永遠不進命令列引數、環境變數值、日誌、例外訊息、回傳內容。
6. **預設不破壞任何東西**：不刪原檔、不覆蓋既有檔。

## 兩個容器方案（由擁有者在 Q1 決定）

| | 方案 A：直接採用 age 檔案格式 | 方案 B：自有的金鑰槽容器（暫名 ISD2） |
|---|---|---|
| 做法 | 用 age 的 Python 綁定（`pyrage`）；自己只寫包裝（CLI、索引、規則） | 只用 `cryptography` 套件，照下方規格實作 |
| 格式由誰設計 | 公開規格（C2SP），有多個獨立實作 | 我們自己組合（原語標準，但**組合是自己的**） |
| 災難時怎麼解 | 任何一台電腦裝公開的 age 工具就能解，不需要我們的程式 | 需要我們的程式；必須把規格與一支獨立的最小解密腳本和備份放在一起 |
| 多把金鑰 | 多個收件者（公鑰），加密端**不需要任何祕密** | 多個金鑰槽（密語或金鑰檔；可加公鑰槽） |
| 換金鑰不重新加密 | 現成工具不提供 | 可以（只重包資料金鑰） |
| 密語模式 | 有，但密語不能和其他收件者並存於同一檔 | 可以混用 |
| 加密後立刻自我驗證 | 需要一個小技巧（見第 4 張文件） | 同一個行程內直接讀回驗證 |
| 相依 | 多一個套件（Rust 編譯的輪檔；本次查到 1.4.0 版有 Windows 輪檔） | 無新增（`cryptography` 是成熟套件） |
| 主要風險 | 綁定套件由個人維護；但檔案格式不綁它 | 自己組合出錯的風險；必須外部審閱與大量負向測試 |

**建議**：以「災難救援」為第一優先時選 A（自己寫的密碼學程式碼越少越好，而且救援不依賴自己的程式）。
若擁有者希望兩個專案只用同一種格式、只相依 `cryptography`、並且需要「換金鑰不重新加密」，選 B，但必須符合下方規格與測試清單，
並在用於唯一一份真實資料之前經過外部審閱。**不論選哪個，下方的 API、CLI、祕密管道、寫檔規則、測試策略都一樣**，
容器實作要藏在同一個介面後面，讓這個決定只影響一個模組。

## 方案 B 的格式規格（ISD2，版本 1）

以下組合方式刻意與 age 的做法一致（隨機檔案金鑰、金鑰槽包裝、檔頭認證、分塊串流），差別只在用 32 位元組檔案金鑰與可換的金鑰槽。
所有整數為大端序。

```
+-----------------------------+
| 魔術字 8 位元組              |  "ISD2" 0x0D 0x0A 0x1A 0x0A（可偵測被當成文字檔轉換）
| 格式版本 1 位元組            |  0x01；不認識就拒絕
| 檔頭長度 4 位元組            |  上限 64 KiB，超過就拒絕
| 檔頭（規範化 JSON）          |  見下
| 檔頭 MAC 32 位元組           |  HMAC-SHA-256
| 分塊 0 … 分塊 n（最後一塊帶結尾標記）|
+-----------------------------+
```

**檔頭欄位**

| 欄位 | 內容 |
|---|---|
| `suite` | `chacha20poly1305-stream`（預設）或 `aes256gcm-stream`；不接受其他值 |
| `chunk_size` | 明文分塊大小，固定 65,536 位元組（欄位保留供日後版本使用；版本 1 只接受這個值） |
| `payload_salt` | 16 位元組隨機值 |
| `slots` | 一到多個金鑰槽，每個槽：類型、該槽的隨機 salt、參數、被包裝的檔案金鑰 |

**金鑰階層**

1. **檔案金鑰**：每個檔案 32 位元組隨機值（作業系統亂數），絕不重複使用。
2. **金鑰槽**（誰可以解開）：
   - `passphrase` 槽：`scrypt(密語, salt, N=2^log_n, r=8, p=1)` → 32 位元組包裝金鑰。預設 `log_n=17`（約 128 MiB 記憶體），
     記憶體充裕時可用 18；解密端接受的範圍是 15～20，超出就拒絕（避免被惡意檔頭耗盡記憶體）。
     若 `cryptography` 版本與其 OpenSSL 支援 Argon2id，可作為第二種槽類型；預設仍用 scrypt 以確保到處都能解。
   - `keyfile` 槽：32 位元組隨機金鑰檔 → `HKDF-SHA-256(金鑰檔, salt, info="isd2 slot keyfile")` → 包裝金鑰。
   - （選配）`x25519` 槽：收件者公鑰；做法照 age 的 X25519 收件者（臨時金鑰交換 → HKDF → 包裝金鑰）。有了它，加密端不必持有任何祕密。
   - 每個槽以 ChaCha20-Poly1305 包裝檔案金鑰；包裝金鑰每槽唯一（因為 salt 隨機），所以 nonce 固定為全零是安全的（與 age 相同的理由）。
3. **檔頭 MAC**：`HMAC-SHA-256(HKDF(檔案金鑰, info="isd2 header"), 魔術字‖版本‖檔頭長度‖檔頭)`。任何檔頭竄改都會在解密第一步被發現。
4. **內容金鑰**：`HKDF-SHA-256(檔案金鑰, salt=payload_salt, info="isd2 payload"‖SHA-256(檔頭))`。把檔頭雜湊綁進內容金鑰，
   檔頭與內容不能被拆開重組。

**分塊串流（STREAM 作法）**

- 每塊明文最多 65,536 位元組，各自做一次認證加密（密文＝明文＋16 位元組標籤）。
- 每塊的 nonce 12 位元組＝11 位元組分塊計數器（從 0 起）＋1 位元組結尾旗標（最後一塊是 `0x01`，其餘 `0x00`）。
  內容金鑰每個檔案都不同，所以計數器 nonce 不會重複。
- 最後一塊可以比較短，但除非整個內容是空的，否則不可為空。讀到檔尾卻沒有遇到帶結尾旗標的分塊＝被截斷，必須失敗。
- 這個做法可以偵測：任一位元被改、分塊被調換、被刪除、被重複、檔尾被截斷或被加料。

**中繼資料**

原檔名、時間、備註等**不放在明文檔頭**。需要保存時，放進加密內容的最前面（一個長度前綴的小 JSON），和資料一起受保護。
明文檔頭只有解密必需的參數。

**已知限制（要寫進使用說明）**

- 檔案大小大致等於原文大小，會洩漏資料量；槽的數量與類型看得到。
- 沒有「寄件者是誰」的證明（不是簽章系統）。
- 密語太弱時，任何拿到檔案的人都可以離線不限次數地猜；scrypt 只能拖慢，不能阻止。

## 函式 API（兩個方案共用）

```python
encrypt_file(src, dst, *, recipients, overwrite=False) -> EncryptResult
decrypt_file(src, dst, *, identity, overwrite=False) -> DecryptResult
encrypt_stream(reader, writer, *, recipients) -> EncryptResult
decrypt_stream(reader, writer, *, identity) -> DecryptResult   # writer 只能是可丟棄的暫存目標
inspect(src) -> HeaderInfo            # 不需要金鑰：格式、版本、槽的類型與數量、大小
verify(src, *, identity) -> VerifyResult   # 完整解密並驗證，但不寫出明文
rewrap(src, dst, *, identity, add=None, remove=None)   # 只有方案 B；至少保留一個槽
read_legacy_isd(src, *, secret_provider) -> LegacyResult   # 只讀舊格式
```

- `recipients`／`identity` 是物件，不是字串：由「祕密提供者」產生（互動輸入、金鑰檔路徑、檔案描述元、作業系統保護的儲存區、
  或擁有者的 USB 鑰匙專案）。核心函式不接受裸字串密語當參數以外的任何來源，也不讀環境變數。
- 結果物件只帶：輸出路徑、位元組數、明文與密文的 SHA-256、槽的指紋。**不帶任何祕密**；`repr` 也不印祕密。
- 錯誤類別固定且訊息不含祕密：`BadInput`、`UnsupportedVersion`、`AuthenticationFailed`（密語錯與被竄改**刻意不區分**）、
  `OutputExists`、`DependencyMissing`、`LegacyFormat`。

## CLI（給人，也給另一個專案呼叫）

```
encrypter-cli encrypt  <來源> --out <目的> (--recipient-file <檔> | --passphrase-prompt | --keyfile <檔>) [--json]
encrypter-cli decrypt  <來源> --out <目的> (--identity-file <檔> | --passphrase-prompt | --keyfile <檔>) [--json]
encrypter-cli inspect  <檔> [--json]
encrypter-cli verify   <檔> (...同 decrypt 的金鑰來源...) [--json]
encrypter-cli keygen   --out <金鑰檔>           # 檔案已存在就拒絕；只印路徑與指紋
encrypter-cli legacy-read <舊.isd> --out <目的> # 只讀舊格式
encrypter-cli --check [--json]                 # 自我檢查：套件版本、原語可用、以暫存假資料往返一次
```

- **沒有任何可以直接放密語的參數。** 密語只能來自：互動提示（不回顯）、`--passphrase-fd <n>`（由呼叫端經管線傳入）、
  或權限受限的檔案路徑。環境變數只允許放「金鑰檔的路徑」，不允許放密語本身（環境變數會被子行程繼承、會出現在當機報告裡）。
- `--json` 輸出照這個 repo 另一個工具已採用的合約：成功 `{"ok": true, "data": {...}}`，失敗
  `{"ok": false, "error": {"code", "reason", "retryable", "remedy"}}`；退出碼 0 成功、2 輸入有問題、3 依賴或環境問題、4 可重試、1 其他。
- 標準輸出與錯誤輸出永遠不印密語、金鑰、明文內容；只印路徑、大小、雜湊、指紋。
- **給 AI 助理呼叫時的規則**（寫進該專案的工具說明）：助理只傳檔案路徑與金鑰檔路徑；不得要求使用者把密語貼進對話；
  解密出來的內容不得被複誦、摘要或寫進記憶；解密與還原屬於需要擁有者當場核准的動作（見第 3 張文件）。

## 寫檔、覆蓋與刪除原檔的規則

| 情況 | 規則 |
|---|---|
| 目的檔已存在 | 拒絕；除非明確給 `--force`（GUI 則是明確的確認對話框） |
| 寫出方式 | 先寫同資料夾的暫存檔 → `flush`＋`fsync` → 原子換名；任何失敗都刪掉暫存檔 |
| 解密 | 邊解邊寫到暫存檔，**最後一塊驗證通過才換名**；失敗就刪掉，不留半成品 |
| 加密後 | 預設立刻讀回並完整驗證一次（可用 `--no-verify` 關閉，但備份流程不允許關） |
| 原始檔 | **預設永遠不動。** `--remove-source` 只有在「讀回驗證通過」之後才執行，而且要明確指定；GUI 預設不提供這個選項 |
| 「安全抹除」 | 不提供、不宣稱。固態硬碟、有快照或同步的資料夾都無法保證覆寫掉舊內容；需要時由整顆磁碟加密負責 |
| 輸入與輸出相同路徑 | 拒絕 |

## 舊 `.isd` 的相容策略：只讀、不再寫

- 新版本**不能產生**任何舊格式的檔案；舊演算法的加密程式碼移除，只留解密。
- 舊檔讀取放在獨立模組（例如 `legacy_isd`），需要舊的函式庫時才載入（列為選用相依，用不到就不裝）。
- 支援範圍：單層、All-In-One、Layered（逐層）、大檔的清單＋分塊、以檔案當金鑰的各種類型、RSA 信封。
- 讀取 CBC／XOR／XOR-FOLD／Base64 的舊檔時，結果要標示「**此檔案的格式無法驗證是否被竄改**」。
- 提供「轉換」流程：讀舊檔 → 以新格式加密 → 讀回驗證 → **不刪舊檔**，由使用者自己確認後處理。
- 動工的第一步：在移除舊的加密程式碼之前，先用現有程式與**假資料**產生一組舊格式樣本檔（每種演算法、每種模式各一），
  當作舊檔讀取模組的已知答案測試資料。

## 測試策略（全部離線、全部假資料）

| 類別 | 內容 |
|---|---|
| 原語已知答案 | ChaCha20-Poly1305（RFC 8439）、scrypt（RFC 7914）、HKDF（RFC 5869）的公開測試向量：確認函式庫接線沒有接錯 |
| 格式已知答案 | 測試時注入固定的亂數來源，產生逐位元組固定的檔案並存成樣本；之後任何改動造成輸出不同都會失敗（方案 A 則改為：用公開的 age 測試向量與參考工具產生的檔案互通） |
| 往返 | 空檔、1 位元組、剛好一塊、一塊加一位元組、多塊、含中文與空格的檔名、多個槽各自都能解 |
| 竄改 | 逐區翻轉位元：魔術字、版本、檔頭長度、檔頭內容、每個槽、檔頭 MAC、任一塊的密文、任一塊的標籤 → 全部必須失敗 |
| 截斷與重組 | 在塊邊界截斷、在塊中間截斷、拿掉最後一塊、調換兩塊、重複一塊、檔尾加料、兩個檔的塊互換 → 全部必須失敗 |
| 錯金鑰 | 錯密語、錯金鑰檔、移除槽之後的舊金鑰、（方案 B）重包之後被換掉的金鑰 → 失敗且錯誤類別相同 |
| 版本與參數 | 不認識的版本、不認識的 `suite`、過大的檔頭長度、超出範圍的 scrypt 參數 → 明確拒絕且不耗用大量記憶體 |
| 不留半成品 | 任何失敗之後，目的資料夾沒有新檔、沒有暫存檔 |
| 不外洩 | 用一個特徵明顯的假密語，確認它不出現在任何回傳、例外、日誌、標準輸出、行程引數 |
| 舊格式 | 上面提到的舊格式樣本逐一解回原文；舊格式寫入路徑不存在 |
| 不覆蓋 | 目的已存在時拒絕；輸入等於輸出時拒絕；沒有驗證通過就不會執行移除來源 |

- 不要加回演算法選單、多階段疊加、重複加密次數。

- 不要為了方便加上「密語放環境變數」或「密語放命令列」。
- 不要在驗證通過前把明文交給呼叫端或寫到最終路徑。
- 不要實作「安全抹除」。
- 不要讓這個工具依賴另一個專案；對方以指令列呼叫。
- 不要在外部審閱之前，把它當成唯一一份真實資料的保護手段。
