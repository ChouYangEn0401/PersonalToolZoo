# 金鑰放哪裡、電腦壞了怎麼救：三種方案比較與建議

- **狀態：待處理（流程與保管是擁有者的事；工具這一側在 0.4.0 已具備，2026-11-13）**：建議的「公鑰加密、一把離線救援金鑰＋一把密語保護的日常金鑰」現在可以直接做——救援金鑰＝萬用鎖（多收件人，`--with-master`），日常金鑰＝`keygen --protect` 的 age 身分檔，`.env` 只放公鑰與路徑。Q2（A+）、Q3（A）、Q6（A，USB 鑰匙先不整合）照建議。見 `20261113-013906-format-decision-age-openpgp.md`。
- 建立：2026-11-12 ｜ 範圍：金鑰的產生、存放、救援流程與演練；含對擁有者 USB 鑰匙專案（usbtether）的唯讀審查結論
- 開發線：`dev/encrypter`
- 前提：`20261112-221100-design-new-crypto-core.md`
- **寫給接手的 agent**：這張是擁有者最在意的部分。任何「金鑰只存在一個地方」的實作都不符合這張的驗收。

## 需求（改寫，非原話）

- 備份的目的是電腦中毒或資料毀損時還救得回來；擁有者目前的想法是把解密用的金鑰放在本機的一個環境設定檔裡。
- 擁有者另有一個自己寫的 USB 鑰匙專案（插著才解鎖），想知道它能不能用在這裡。

## 問題一句話

**金鑰如果只放在要被備份的那台電腦上，電腦一出事，金鑰會和資料一起消失，備份就打不開**；所以重點不是「放哪個檔」，而是「至少有一份離線的、不依賴這台電腦的救援金鑰」。

## 結論先講

1. **不建議**把解密金鑰只放在本機設定檔（方案 C 單獨使用）：它正好在最需要它的時候不見，而且本機的惡意程式讀得到。
2. **建議的做法**是方案 A 的加強版：備份用**公鑰**加密（做備份的電腦上根本不放解密金鑰），解密金鑰有兩把——
   一把**離線救援金鑰**（紙本＋密碼管理器，平常不碰），一把**日常金鑰**（用密語保護，做演練與平常還原用）。
3. 擁有者的 USB 鑰匙專案適合當**「人在場、同意這次動作」的憑證與日常金鑰的便利解鎖**，不適合當唯一的備份金鑰。

## 三種方案比較

| | A：密語（存密碼管理器）＋離線救援金鑰 | B：USB 鑰匙（usbtether） | C：金鑰檔放本機設定檔（另外自行備份） |
|---|---|---|---|
| 電腦毀損／被加密勒索後還打得開嗎 | 可以（密語在腦中或密碼管理器，救援金鑰在別處） | 隨身碟沒壞、沒一起遺失才可以；隨身碟是單點 | **不行**，除非「另外備份」真的做了而且沒過期 |
| 本機有惡意程式時 | 輸入密語的那一刻會被側錄；但平常不輸入就不暴露 | 插著的時候金鑰檔可被讀走（一般隨身碟無法藏金鑰） | 隨時可被讀走（設定檔就是一般檔案） |
| 平常做備份要不要輸入東西 | 不用（用公鑰加密） | 不用 | 不用 |
| 還原時的麻煩程度 | 輸入密語 | 插隨身碟 | 無 |
| 忘記／遺失的後果 | 密語忘了還有救援金鑰；兩者都沒了就救不回 | 隨身碟壞掉或重新登記就救不回 | 檔案沒了就救不回 |
| 被誤傳到版本控制或雲端同步的風險 | 低 | 低 | **高**（設定檔很容易被一起打包、同步、提交） |
| 適合的角色 | **主要方案** | 便利因子、核准用 | 只能當「指向金鑰位置的設定」，不能放金鑰本體 |

## 為什麼「只放本機」不行（方案 C 的重點分析）

- **同生共死**：備份要防的情境是這台電腦中毒、硬碟壞、被勒索軟體加密。金鑰若只在這台電腦上，這些情境裡它會一起沒有。
  「另外自己備份金鑰檔」如果沒有變成固定流程與定期檢查，實務上等於沒有。
- **惡意程式讀得到**：設定檔是以使用者身分可讀的一般檔案。任何以同一個帳號執行的程式（包含被植入的套件、瀏覽器外掛的本機元件）
  都能讀。若攻擊者也拿得到備份檔（例如雲端帳號被盜），就能解開全部歷史備份。
- **容易外流**：設定檔常被編輯器外掛、備份腳本、打包工具、AI 助理的檔案讀取順手帶走；一次誤提交到公開的版本庫就無法收回。
- **用作業系統的保護機制把它封起來**（例如 Windows 的使用者層級資料保護）可以擋掉「別的帳號、別台電腦」，
  但擋不了同一個帳號下的惡意程式，而且封起來之後更是**綁死在這台電腦**——電腦壞了就打不開。所以它只能保護「日常金鑰」，
  不能取代離線救援金鑰。

**如果擁有者仍想保留那個本機設定檔**：讓它只放「金鑰檔的路徑」與「公鑰（收件者）」；放在那裡的日常金鑰檔本身必須是被密語保護的；
並且把它加進忽略清單、不進任何備份包的明文部分。

## 建議方案的具體設計

### 金鑰角色

| 金鑰 | 用途 | 放在哪 | 多久用一次 |
|---|---|---|---|
| **備份公鑰**（收件者清單） | 加密備份 | 本機設定檔、備份腳本旁（公開也無妨） | 每次備份 |
| **離線救援金鑰** | 災難時解開備份 | 兩份以上、不同地點：紙本（列印的救援卡）＋密碼管理器的安全筆記；可再加一支放在別處的隨身碟 | 只在演練與災難時 |
| **日常金鑰** | 平常還原單一檔案、每月演練 | 本機，但檔案本身以密語加密；密語在密碼管理器 | 偶爾 |
| （選配）USB 鑰匙 | 讓日常金鑰不必打密語、以及核准「還原／解密」動作 | 擁有者的隨身碟 | 偶爾 |

每份備份同時加密給「救援金鑰」與「日常金鑰」兩個收件者，任何一把都能解。做備份的那台電腦平常**只有公鑰**，
所以即使它被入侵，攻擊者也拿不到能解開歷史備份的東西（當然，他仍看得到電腦上當下的明文資料——這不是加密能解決的）。

### 救援卡（紙本）

- 內容：救援金鑰本體（文字與 QR 碼各一）、建立日期、金鑰指紋、「用什麼公開工具與哪個指令解開」的三行說明、備份放在哪裡的提示（不含帳號密碼）。
- 產生時直接送到印表機或顯示在螢幕上抄寫，**不存成檔案**；產生的過程不經過任何 AI 助理、不進對話、不進日誌。
- 至少兩張，放在兩個不同的實體地點。
- 救援金鑰**不要**放進它自己保護的備份裡（循環依賴）。

### 密語規則

- 用隨機產生的密語（例如六個以上隨機單字，或二十個以上隨機字元），不要自己想。密語夠強時，金鑰衍生函式只是第二道保險。
- 密語只存在密碼管理器與擁有者的記憶裡；不寫進任何設定檔、腳本、筆記軟體、對話。

### 救援流程（寫成一頁、和救援卡放一起）

1. 找一台乾淨的電腦（不是出事的那台）。
2. 安裝公開的解密工具（選方案 A 容器時是 age；選自有容器時是和備份放在一起的獨立解密腳本＋規格）。
3. 從備份位置下載最新一份備份與它的校驗檔，先核對校驗值。
4. 用救援卡上的金鑰解開 → 得到索引 → 依索引解開需要的項目。
5. 版本庫類的備份：驗證打包檔、還原到新資料夾、檢查歷史完整。
6. 還原完成後：**視同舊的日常金鑰已外洩**，產生新的日常金鑰；若出事原因是入侵，救援金鑰也要換，並用新金鑰重新加密之後的備份。

### 定期演練

| 頻率 | 做什麼 | 通過條件 |
|---|---|---|
| 每次備份後（自動） | 讀回剛產生的加密檔做完整驗證；核對校驗值 | 驗證通過才算備份成功 |
| 每月（自動提醒、人按一下） | 用日常金鑰把最新一份備份解到暫存資料夾，比對索引裡的雜湊；版本庫打包檔做驗證 | 全部相符；演練紀錄寫一行（日期、備份代號、結果，不含祕密） |
| 每季（人工，約 20 分鐘） | 在**另一台電腦**上，只用救援卡＋下載的備份＋公開工具，完整走一次救援流程 | 能還原出一個指定的檔案與一個版本庫；確認救援卡還讀得出來 |
| 金鑰變更後 | 立刻做一次每季演練 | 同上 |

演練失敗＝備份不存在。演練紀錄連續兩次缺漏時，備份工具應該在每次執行時顯示警告。

## 擁有者的 USB 鑰匙專案（usbtether）審查結論（只讀，未執行）

沒有執行、沒有安裝它的套件。閱讀範圍：金鑰、登記、挑戰回應、授權、保險箱、裝置識別與探測等核心模組，以及協定、威脅模型、
架構、裝置識別四份文件是**全文**；桌面面板、網頁示範、命令列與打包設定看的是結構與關鍵段落；測試只看了名稱與保險箱那一份的內容。
下面的結論不依賴沒有細讀的部分。

### 它是什麼

把一支普通隨身碟變成「插著才有效」的憑證：隨身碟上放一把 Ed25519 私鑰，主機端的登記簿記錄公鑰與這支隨身碟的硬體識別
（廠商代碼、產品代碼、序號）。驗證時主機發一次性的挑戰，代理程式用隨身碟上的私鑰簽名並附上它觀察到的裝置資訊，
主機核對簽章與硬體識別。上層再提供工作階段、幾秒內有效且只能用一次的能力憑證、拔除即撤銷，以及一個以隨身碟金鑰加密資料夾的保險箱功能。

### 做得好的地方

| 項目 | 觀察 |
|---|---|
| 誠實的威脅模型 | 文件明講它是「便利等級」：擋得住隨手複製，擋不住能偽造 USB 描述元的裝置與被入侵的主機；還有一個測試專門斷言「偽造描述元會被接受」，讓這個限制不會被忘記 |
| 挑戰回應 | 挑戰一次性、30 秒過期、綁定用途；簽章涵蓋協定名稱、nonce、用途、憑證代號與裝置資訊；先消耗挑戰再驗證 |
| 規範化編碼與領域分隔 | 被簽與被雜湊的內容都用固定排序的 JSON，並以協定識別字開頭 |
| 登記流程是交易式的 | 寫入順序有「提交標記」；登記後立刻自我測試；任何一步失敗就把隨身碟、登記簿、主機祕密全部回復 |
| 原子寫檔 | 暫存檔 → 寫入 → 同步到磁碟 → 換名 |
| 主機祕密儲存的抽象層 | 可替換的介面；Windows 上用作業系統的使用者層級保護封存 |
| 能力憑證 | 範圍只含一個（資源、動作）、單次使用、幾秒過期、以只存在記憶體的金鑰做 HMAC；工作階段撤銷後全部失效 |
| 測試 | 約 180 個測試函式（只數過、沒有執行），涵蓋重放、用途挪用、竄改、複製到別支隨身碟、撤銷、回復、路徑穿越；有不需要硬體的記憶體內探測器，可以完全離線測試 |
| 工作副本的收尾 | 開啟加密檔的輔助程式被強制結束後，下次執行會把未存回的變更加密回去並清掉明文副本 |

### 用在備份金鑰上會有問題的地方

| 項目 | 觀察 | 對備份的影響 |
|---|---|---|
| 保險箱金鑰的來源 | 用私鑰對一段固定文字簽名，再把簽章經 HKDF 得到 32 位元組金鑰 | 可以運作（Ed25519 簽章依規格是決定性的，而且「挑戰簽章」與「衍生簽章」的前綴不同，不會互相冒用），但**不是標準的金鑰衍生做法**：同一把金鑰既簽名又當加密金鑰的來源；若日後換成會加入隨機性的簽章實作，金鑰會無聲地改變、舊資料打不開；也沒有金鑰版本與輪替 |
| 重新登記 | 重新登記會產生新私鑰 | 舊金鑰加密的檔案**永久打不開**（它的文件與示範頁有警告） |
| 單點 | 金鑰只在一支隨身碟上；隨身碟是容易壞、容易掉的東西 | 不能當唯一的救援手段 |
| 金鑰可被複製 | 私鑰是隨身碟上的一般檔案；硬體識別只影響「驗證」這一步，**不影響金鑰衍生**——拿到私鑰檔的人自己寫幾行程式就能算出保險箱金鑰 | 「插著才解得開」是使用流程上的限制，不是密碼學上的限制 |
| 保險箱檔案格式 | 整個檔案一次讀進記憶體；同一把長期金鑰配隨機 nonce；加密後預設**刪除原檔**且沒有先讀回驗證；檔名原樣保留只加副檔名；只有一個四位元組的魔術字，沒有 KDF 參數與金鑰識別 | 不適合大檔、不適合當備份格式；檔名會洩漏內容 |
| 登記簿 | 主機上的 JSON 檔，沒有簽章也沒有加密（文件有寫） | 能寫這個檔的人就能登記新憑證 |
| 自動解鎖模式 | 主機祕密以使用者層級保護封存 | 同一帳號下的惡意程式可以無聲地解鎖（文件有寫） |
| 以密語保護私鑰時的抗暴力強度 | 用函式庫預設的私鑰加密方式 | **推測**其預設的密語衍生次數偏低，尚未查證；若要依賴它，需明確指定較強的參數 |
| 拔除偵測 | 輪詢，約一秒 | 對備份無影響；對「拔掉就立刻鎖」的期待要有落差的認知 |

### 可以借用的

- **寫檔與交易的做法**：原子寫入、提交標記、失敗全部回復、登記後自我測試。新核心的寫檔規則直接照這個做。
- **規範化編碼＋領域分隔＋用途綁定**：新核心的檔頭認證與金鑰衍生標籤照這個精神寫。
- **「一次只核准一個動作」的能力憑證模型**：用在 AI 助理那一側——「解密／還原」這類動作要擁有者插著鑰匙、當場取得一張幾秒內有效、
  只能用一次、只對這個檔案這個動作有效的憑證才放行。這是它最適合的角色：**擁有者金鑰（核准與解鎖）**。
- **主機祕密儲存的介面**：拿來當新核心「祕密提供者」的其中一種實作（保護日常金鑰）。
- **誠實寫限制、把已知限制寫成測試**的文件風格。
- **記憶體內的假裝置**：讓整合測試可以離線、不碰硬體。

### 不要借用的

| 不借用 | 理由 |
|---|---|
| 「簽固定文字再 HKDF」當備份資料的金鑰來源 | 非標準、沒有版本與輪替、重新登記即失去金鑰。若要讓鑰匙參與，應該是**用它包住一把獨立產生的隨機金鑰**（多一個金鑰槽），而且永遠另有救援金鑰 |
| 它的保險箱檔案格式 | 見上表：不串流、檔名外露、沒有參數欄位、長期金鑰配隨機 nonce |
| 加密後預設刪除原檔 | 與新核心「預設不破壞、驗證後才可選擇移除」相反 |
| 把 USB 硬體識別當成安全邊界 | 它自己的文件就說明這擋不住有心人 |
| 自動解鎖模式當唯一保護 | 綁死在這台電腦與這個帳號，電腦壞了就沒了 |
| 網頁示範 | 是實驗用途，不是服務；而且這台電腦不開任何網路埠 |

### 給該專案的建議（只是建議，不在這裡改它）

- 若要繼續提供檔案加密，建議把「衍生金鑰」改成隨身碟上另存一把獨立的隨機祕密（或一把金鑰交換用的金鑰），並帶版本號；
  「簽章衍生」保留為舊版相容。
- 重新登記前，檢查是否仍有用舊金鑰加密的檔案，並要求先解開或先包給新金鑰。

## 選項表

| 選項 | 內容 | 建議 |
|---|---|---|
| A+ | 公鑰加密；離線救援金鑰（紙本＋密碼管理器）＋密語保護的日常金鑰；USB 鑰匙為選配的便利與核准因子 | **建議（預設）** |
| A | 只有密語（密碼管理器）＋離線救援金鑰，不用公鑰 | 可行；做備份時電腦上需要有能加密的祕密，較弱 |
| B | 只用 USB 鑰匙 | 不建議：單點、可複製、重新登記即失去 |
| C | 只放本機設定檔 | 不建議：與資料同生共死、惡意程式可讀 |

## 驗收

- [ ] 做備份的流程在電腦上找不到任何能解開備份的祕密（只有公鑰）
- [ ] 產生金鑰的指令不把金鑰印到會被記錄的地方；救援卡不落地成檔案
- [ ] 把本機所有金鑰檔與設定檔刪掉（在測試環境以假金鑰模擬），仍能只靠「救援金鑰＋備份檔」完整還原
- [ ] 每月演練與每季演練各有一支指令或一頁步驟，並會留下不含祕密的演練紀錄
- [ ] 文件明確寫出：哪些情況救不回來（救援金鑰與日常密語同時遺失）
- [ ] 若整合 USB 鑰匙：拿掉鑰匙仍可用救援金鑰還原（以測試證明）；整合測試只用記憶體內的假裝置

## 不要做的事

- 不要讓任何金鑰只存在一個地方。
- 不要把解密金鑰或密語寫進本機設定檔、腳本、版本庫、對話、日誌。
- 不要把救援金鑰放進它自己保護的備份。
- 不要用 USB 鑰匙衍生出來的金鑰直接加密備份資料。
- 不要在這台電腦上對真實隨身碟或真實金鑰做測試；硬體相關的實測由擁有者自己做。
- 不要修改擁有者的 USB 鑰匙專案；建議寫在這裡，由擁有者決定要不要採納。
